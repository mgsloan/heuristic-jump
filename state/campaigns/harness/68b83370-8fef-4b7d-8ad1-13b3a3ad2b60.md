## Hypothesis

All three are open for one reason, and it is written down rather than
inferred: `loops.md#what-is-deliberately-not-built-yet` lists "the
frontier, the evaluation half of held-out selection" as deferred, on the
argument that "a thing that only serves tuning loops is not built before
there are tuning loops". So this is not a defect anyone has missed — it is
a deferral the audit reports as three gaps because the audit judges
sections against the code and cannot see §18's exemption.

The same section says what ends the deferral: "**This list shortens as the
followup is built, and it is the list rather than the argument that
moves**", and §18 "points the conformance loop at this document precisely
so that they cross it during phase 1.5". Building the phase-2 machinery
during phase 1a is what this loop exists for.

So the hypothesis is that the frontier is buildable *now*, without a
corpus, because it is arithmetic over rows whose shape §10 specifies — and
that the half which genuinely cannot be built now is only step 2 of the
gate selection (the corpus run), which is `measure_<lang>`'s and outside
every path this loop owns. If that is right, the deliverable is: the
frontier object, the progress term that reads it, a selection command that
*refuses* to select on tuning numbers alone, and three lines struck from
§18's list.

The thing to be careful about is the progress term. Adding a disjunct to
`progress` is a metric redefinition, so it gets a rule number and a
backtest before it decides anything live.

## Outcome

Confirmed. The hypothesis held exactly: the frontier is arithmetic over
rows whose shape §10 specifies, and the only genuinely unbuildable half was
step 2 of the gate selection — the corpus run — which is `measure_<lang>`'s
and outside every path this loop owns.

The thing that made this campaign cheap, and which the hypothesis did not
anticipate, is that the shapes were *already in the repository*.
`shared::record::QueryRecord` is a complete type carrying every field §10's
row spec names, and the doc comment on `measure_core`'s `write_records`
says outright: "Digesting these into something readable is the harness's
job, not `measure_core`'s." That is the difference between this and the
`ccusage` dead end two campaigns ago — the producer's output shape was
readable from the source rather than guessed, so the digest could be
written and fixtured against the real spelling without the tool ever
running.

What is left of §12 and of §10's selection is one thing and it is not
mine: something has to *produce* `state/heldout/<language>.jsonl`, which
needs a corpus, a handler, and a path this loop is denied. Every consumer
of that file now exists and refuses honestly without it.
