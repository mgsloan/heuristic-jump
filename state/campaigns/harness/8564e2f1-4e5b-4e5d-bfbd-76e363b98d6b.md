## Hypothesis

Every one of these is the same defect: a number the design names is computed
approximately, or computed and then never read. Nothing here needs new
machinery — the metrics rows, the campaign close and the gate's step 7
already run every time; they just do not look at the values. So the work is
arithmetic and predicates in one file, and the risk is entirely in the
blast radius: `hj` computes every loop's number, and the core loop runs three
workers against it.

Two constraints taken deliberately:

- **Do not edit `harness/gate`.** The ratchet goes in `check-metrics`, which
  the gate already calls at step 7. §4 scopes the gate's "ratchets" step to
  §11's *size* ratchets, phase 3 only; §7's test-count ratchet is a different
  mechanism and belongs with the metric row. This also leaves the reviewed
  gate untouched, which is the second half of [9b48ca324c].
- **No new file that `hj record` rewrites per campaign.** Three workers
  bumping one scalar in one file conflict on rebase, and `merge_back` reads a
  conflict as "two loops wrote the same file". The ratchet baseline is
  therefore derived from the append-only metrics history, with
  `harness/ratchets.toml` as a hand-set floor.
