## Target

`core.md#5-deadlines-and-abstention`, its second gap:

> the cap is configurable via --deadline-ms, defaulting to 750ms proxying and
> 2000ms standalone, and the driver hard-caps by dropping the result of any
> handler that returns after the deadline

Picked because it is the section closest to going clean, and the number moves
per section. §5 has two gaps; the first one — `Deadline` with `at`,
`cancelled` and `expired()` — was satisfied by `crates/shared/src/deadline.rs`
in an earlier campaign, and its audit entry is stamped `03:47:22`, from before
any code existed. So one gap's worth of work should take the whole section
from `gaps` to `clean`. Every other single-gap section needs a crate that does
not exist (`measure_core`, `similarity`) or a subsystem that does (the
document map, the frame codec, the trace record).

## Hypothesis

Both halves of the claim are implementable in phase 1a without a shim:

* The defaults are a pure function of the mode, and the mode is a pure
  function of whether a server command was given (`deps.md` §11: `server.is_
  empty()` *is* the mode). That is a `driver::config` module and a test that
  needs no I/O.
* The hard cap does not need a caller with a real handler. `Query` already
  carries the `Deadline`, so `dispatch` itself can drop a late `Outcome`, and
  the decision can be factored into a function over `(&Deadline, Dispatched)`
  that a test can drive with a `TestClock` — no `tree_sitter::Language`, which
  is what makes a full dispatch test impossible until `lang_rust` exists
  (journal, `e3b8dbf4`).

The risk is scope: `--deadline-ms` lives on a `clap` `Cli` in `heuristic_jump`
whose other flags (`--trace`, `--log`) belong to sections this campaign does
not target, and `main` has nothing to hand a resolved config to until
`driver::run` exists.
