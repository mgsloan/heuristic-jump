## Outcome

Confirmed, as far as a loop can establish it — the auditor decides whether the
section goes clean. Both gaps have code and a test asserting the claim, and the
section's one `minor` is reconciled (provisional decisions 4 -> 3).

The one judgement call was what "normalized text form" means for an id that is
JSON's `number | string`. `EditorRequestId` holds the id's **JSON** text: `42`
stays `42` and `"42"` stays `"42"`, with escapes decoded and the string requoted
by JSON's mandatory set. Reasons, in the order they decided it:

* A decoded form collides the number `42` with the string `"42"`, which are
  different requests, in the map `shim.md` §7 keys by exactly this type.
* §8.2 has the response envelope echo the id back, and LSP wants the echo
  identical. JSON text can be copied; a decoded form has to be re-encoded from
  a kind it no longer knows.
* Requoting by `serde_json`'s own rule — and not one character wider — is what
  makes that echo a copy rather than a re-encoding.

Not a decision record: it trades nothing off. The alternative considered was a
kind tag plus decoded content (`n42` / `s42`), which is the same information in
a form that has to be untagged before it can be echoed and is not "text form"
in any sense a reader of §1 would recognise.

Not done, deliberately: `LanguageId` and `FileExtension` are still not
`Deserialize` and should not be. They are interned `&'static str` resolved
against the registry, and §1 requires an unknown language to fail *at the
boundary* rather than travel inward — an impl would have to leak or intern an
arbitrary string.

than from the implementation: `crates/similarity/` is denied to every loop but
