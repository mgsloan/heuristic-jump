## Hypothesis

The `didSave` gap is the one thing in this assignment that is genuinely
unbuilt, and `actor.rs` names its own blocker: "a `Job` *is* a query — a
handler, a seed, a position and an answer — and a checksum read is a second
kind of job with a second kind of reply, which nothing builds". So the work is
a second job kind in `workers.rs`, not a read anywhere.

The part that is not in the gap text and that I expect to be the real content:
**the read is asynchronous now, so the comparison can race the buffer.** A
`didChange` between the `didSave` and the worker's read makes the file and the
rope differ legitimately, and comparing them then distrusts a document that
never drifted — §8.6's rule firing on its own latency. `TreeFate` already
argues that a version comparison does not close this (a `didOpen` resync
replaces the text at a version we have seen), so the guard has to be a stamp
of our own.
