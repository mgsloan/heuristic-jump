## Target

Three gaps, one per section, all naming the same absence — nothing in `driver`
ever realises a `SnapshotSeed`:

* **`core.md#2-document-snapshots[d1cd7205ef]`** — "`driver` builds a snapshot
  at dispatch and `measure_core` builds one per recorded position, both through
  the same constructor in `shared`". `measure_core`'s half is done
  (`positions.rs:139`, `replay.rs:110`); `dispatch` receives a `Query` whose
  `doc` was built by somebody else.
* **`core.md#snapshots-are-o1-to-take-and-are-parsed-before-a-handler-sees-one[b0dd5a5689]`**
  — "the parse still happens inside the worker and inside the deadline;
  `realise` is called by the worker, never by `core`". `realise` takes no
  `Deadline`, cannot observe one, and passes `None` where tree-sitter's
  progress callback goes.
* **`core.md#text-and-tree-can-never-disagree[bba4dcbe79]`** — "the dispatch
  wrapper — not the handler — sends `Parsed { uri, version, tree }` to `core`
  after `realise` succeeds, and `core` caches it so the next query starts
  warm". No `Parsed` type, no tree cache, and nothing ever fills
  `SnapshotSeed::incremental`'s `base`.

One sentence for why they belong together: they are the same piece of work —
*the dispatch wrapper builds the handler's snapshot on the worker thread,
under the deadline, and hands the tree back for `core` to cache* — seen from
three sides, and no one of them can be closed without writing the other two.
Each section has exactly one gap, so closing all three is +3 sections.

## Hypothesis

The two-step seed/realise split already exists and is correct; what is missing
is its only shipping consumer. `dispatch` takes an already-realised `Query`
because the campaign that wrote it needed one, not because anything blocks
building the seed there. Expected to be ordinary code plus one signature
change in `shared`.

The one thing that may not be ordinary: `realise` gaining a `&Deadline`
contradicts §2's printed `pub fn realise(self) -> Result<DocumentSnapshot,
Error>` while making §2's own prose ("inside the deadline") true. Class A if
so, and the changelog entry has to say plainly that the same campaign edited
the document and the code it describes.

Expected risk: tree-sitter's parse progress callback may not fire at all on a
document small enough for a fixture, which would make "the parse is bounded"
untestable at fixture scale. That is a result, not a failure — it would mean
the deadline can only be observed *between* parses, and the section's claim
would need narrowing rather than the code needing a lock.

## Experiments

1. `realise` takes the `&Deadline` it parses under and abandons the parse
   through tree-sitter's `ParseOptions` progress callback, reporting
   `HandlerError::DeadlineExpired` — the one class `dispatch` maps back to an
   abstention. Five tests in `crates/shared/tests/document.rs`; the two
   deadline ones verified to fail without the callback before being kept.
   Gate green, `e90bf6d`. CHANGE-conformance-013 for §2's printed signature.
2. `dispatch` takes a `Request` carrying the seed, realises it on the worker
   thread and builds the `Query` itself. Asserted by the handler *not being
   called* when the parse runs out of time, which is the only thing that
   distinguishes the wrapper's ordering from `hard_cap`'s. Gate green,
   `55edb5c`.
3. `Parsed` and `TreeCache`: the wrapper mints the first, the cache's only
   write consumes it, and the cache is the only thing that fills
   `SnapshotSeed::incremental`'s `base`. `ParseKind` added to `shared` to make
   the branch observable at all. Both new claims verified to fail before being
   kept. Gate green, `321ff36`.

## Outcome

**Confirmed.** All three gaps closed and committed; the loop is
`TreeCache::seed` → `dispatch` → `Parsed` → `TreeCache::insert`, and
`crates/driver/tests/snapshots.rs` drives one full turn of it.

`[b0dd5a5689]`: `realise(self, &Deadline)` installs a progress callback that
breaks on `expired()` and reports `HandlerError::DeadlineExpired`, so a
document too large to parse inside the budget abstains rather than failing —
the difference §7's record is built to keep. Measured rather than assumed:
tree-sitter checks the callback once per 100 parser *operations*, so a 46 KB
file is reliably abandoned and a 60-byte one is not. Both asserted.

`[d1cd7205ef]`: `dispatch(handler, Request { seed, .. }, encoding)` realises
the seed and builds the `Query` itself, so a handler cannot be handed a
document nobody parsed. `realise` remains the only route to a
`DocumentSnapshot` anywhere — its `tree` field is private and there is no
other constructor — which is the mechanical check the gap asked for.

`[bba4dcbe79]`: `Parsed`'s constructor is private to `dispatch` and
`TreeCache::insert` consumes one by value, so "the wrapper sends it, the
handler cannot forget" is a property of the types. What is still absent is the
channel: `core` does not exist, so `Parsed` travels by return value.

Three things carried forward, at length in the journal: the progress
callback's granularity is an operation count and not a byte count; folding
`Parsed` into `Dispatched::Decided` is wrong because the parse succeeded
independently of the decision; and `ParseKind` exists because an incremental
reparse and a full one are indistinguishable in their result, which is exactly
what let the missing `base` stay invisible.
