# Existing Tooling for a Ralph-Loop `heuristic-jump` Harness: What to Adopt, Steal, and Build

**Bottom line up front:** Most of your harness is genuinely reinventable from off-the-shelf parts — the loop runner, monitoring, worktree orchestration, edit-scope enforcement, ratchets, adversarial review, ADRs, and snapshot testing all have mature, actively-maintained tools you should adopt or steal from. But the two things at the *core* of your design — a **status-monotonic spec ledger whose transitions are gated on a named passing test**, and a **mechanical metric oracle that shows the loop a verdict, not the numbers, behind a filesystem boundary** — have no real off-the-shelf equivalent and should stay bespoke. Adopt a boring loop runner and Bencher for metric ratchets; keep your ledger and oracle custom.

## TL;DR
- **Adopt 3-5 things now:** a thin Ralph loop runner instead of hand-rolling (`wreckit`, `loopgate_harness`, or the official `ralph-wiggum` Claude Code plugin as reference only); **Bencher** (dual Apache-2.0/MIT, self-hostable) for *all* your numeric ratchets — binary size, test count, and per-stratum accuracy — since it tracks arbitrary metrics with statistical thresholds and fails CI on regression; **insta + cargo-nextest** for the golden `truth.jsonl` replay; Claude Code's native **`PreToolUse` hooks + `/sandbox`** for edit-scope enforcement; and **CodeRabbit or Claude's own `/review`** as the surface for your adversarial verifier.
- **Keep bespoke:** the `spec/ledger.toml` with test-gated monotonic status, the metric harness with held-out sets physically outside the worktree, the verdict-not-numbers boundary, and the `DECISION-NNN` grep-as-report convention. No SDD framework (Spec Kit, Kiro, OpenSpec, BMAD) enforces "status can only advance when a named test passes," which is the whole point of your design.
- **Known dead ends / over-thinking to correct:** don't build worktree plumbing by hand (Conductor/Crystal/vibe-kanban/claude-squad do it, though most are macOS- or GUI-first and may fight a headless loop); don't build a cost/stall dashboard from scratch (ccusage + OpenTelemetry→Grafana already exist); and the "different model vs. different session" verifier question is largely solved in practice — a fresh session with no memory already captures most of the benefit, and cross-model review is cheap to add via a second CLI.

## Key Findings

1. **The Ralph loop is now a commodity pattern.** Since Geoffrey Huntley's canonical post "Ralph Wiggum as a software engineer" (ghuntley.com/ralph), first shared in tweets dated July 13, 2025 — where he wrote *"Frequent question: how do you plan? I don't. The models know what a compiler is better than I do. I just ask it."* — there is now an official Anthropic `ralph-wiggum` Claude Code plugin plus a half-dozen open harnesses. Your `while :; do cat PROMPT.md | claude -p; done` instinct is correct and community-endorsed — the value is in your *gates and state files*, not the loop.
2. **Your spec ledger is the crown jewel and is not sold anywhere.** Every SDD framework produces markdown/JSON artifacts an agent reads, but none enforce a *monotonic, test-gated* status machine. Requirements-traceability tools (OpenFastTrace, Doorstop, StrictDoc) come closest on the "link requirement→test" axis but are heavyweight and not agent-facing.
3. **Bencher solves subsystems 7 and 9's numeric core in one tool.** It ingests arbitrary metrics (accuracy, byte counts, test counts) via BMF JSON, offers seven statistical threshold models, is self-hostable and open source, and fails CI on regression. This directly replaces the bespoke ratchet-file logic you were going to write for binary size, test count, and per-stratum accuracy.
4. **Edit-scope enforcement is now native to Claude Code.** `PreToolUse` hooks + the `/sandbox` (Seatbelt/bubblewrap) system + `denyRead`/`denyWrite` cover exactly your "reject edits outside owned paths" and "agent can't read held-out data" requirements — with the important caveat that Read/Edit deny rules don't stop `cat` in a bash subprocess, so the filesystem boundary must be OS-level, not rule-level.
5. **The adversarial verifier maps onto existing AI code review, but "spec-conformance review" specifically is a prompt you own.** CodeRabbit, Greptile, Bugbot, and Claude's `/review` all do generic PR review; none do "given this spec section, where does the implementation diverge?" out of the box — but that's a prompt + a read-only session, not a product.

## Details by Subsystem

### 1. The loop runner
**Verdict: Steal ideas / adopt a thin runner; do not build much.**

The Ralph pattern is exactly what you described: one fixed prompt, fresh context each iteration, filesystem as memory, model picks highest-value item, commits, exits. Huntley's canonical posts (ghuntley.com/ralph, github.com/ghuntley/how-to-ralph-wiggum) established it in mid-2025, and there is now a spectrum of implementations:

- **`anthropics/claude-plugins-official` → `ralph-loop`** and the in-repo `anthropics/claude-code/plugins/ralph-wiggum`: the *official* plugin. `/ralph-loop "..." --max-iterations N --completion-promise "DONE"`. **Important caveat matching your design:** this plugin uses a **stop hook to re-feed the prompt in the same session**, which the Ralph community explicitly considers "missing the point" — Michael Arnaldi: *"If you're implementing Ralph as part of the agent harness via skill/command/etc you are missing the point of Ralph which is to use always a fresh context."* Your fresh-`claude -p`-per-iteration design is the correct one; use the plugin only as a reference. There is also an open bug (anthropics/claude-code#18086) where max-iterations wasn't respected and produced 636 empty iterations — a point in favor of your own bounded bash loop.
- **`mikehostetler/wreckit`** (`npm i -g wreckit`): a CLI Ralph runner "over your roadmap: ideas → research → plan → implement → PR → done," file-based state in `.wreckit/`, designed for multi-actor parallelism across sandboxes. Closest in spirit to your design.
- **`rxdt/loopgate_harness`**: "A repo-native coding-agent loop harness for Claude, Codex, Copilot… Agents can edit. Gates decide what lands." *Strikingly* close to your architecture — `docs/PROMPT.md` + `docs/specs/`, gates that "bound what any commit may touch," worker-agnostic. Worth reading before you write a line.
- **`frankbria/ralph-claude-code`**: adds intelligent exit detection, session/rate-limit handling, and — notably for subsystem 10 — **built-in stall heuristics**: `MAX_CONSECUTIVE_TEST_LOOPS`, `MAX_CONSECUTIVE_DONE_SIGNALS`, `TEST_PERCENTAGE_THRESHOLD` (flag if ≥30% of loops are test-only). A direct precedent for your "N consecutive iterations with no ledger advance" stall detector.
- **`yoshpy-dev/ralph`** and **`syuya2036/ralph-loop`** (agent-agnostic: Claude, Codex, Gemini, Ollama): scaffolding harnesses.

**Claude Code native features that cover runner needs:** headless `claude -p --output-format json`, the Agent SDK (embedding a loop in your own program), `anthropics/claude-code-action@v1` (GitHub Actions, launched Sept 29 2025, gives a live shell), subagents, skills, hooks, background tasks. For a single dev valuing boring runners, the honest recommendation: **write the ~20-line bash loop yourself** (you keep full control of exit codes, gates, and commit trailers) and **steal the stall-detection constants from `frankbria/ralph-claude-code`**. Adopting a whole harness would fight your "rich state files over clever orchestration" principle.

### 2. Monitoring UI / TUI / dashboard
**Verdict: Adopt off-the-shelf; do not build.**

For cost and session monitoring the ecosystem is mature:
- **`ccusage`** (`npx ccusage@latest`): parses Claude Code's local JSONL logs offline, no API key, daily/monthly/session/5-hour-block cost reports with per-model breakdown. The de facto standard.
- **Claude-Code-Usage-Monitor**: live terminal dashboard with ML-based burn-rate prediction ("predicted exhaustion of the active billing window").
- **`ccflare`** (web dashboard), **ccstatusline** (status-line metrics), **claude-doctor** (config diagnostics).
- **OpenTelemetry path**: Claude Code emits OTel (`CLAUDE_CODE_ENABLE_TELEMETRY=1`, `service.name=claude-code`) → SigNoz/Grafana/Prometheus/Datadog. `jeremyeder/ccusage-graphs` gives a Docker Prometheus+Grafana stack.

For watching *diffs and progress* across long runs, the worktree GUIs (Conductor, Crystal, vibe-kanban — subsystem 3) double as monitoring dashboards. The general LLM-observability platforms (LangSmith, Langfuse, Braintrust, W&B Weave, Helicone, Arize/Phoenix) are overkill for a single-dev mechanical-metric project and would fight your simplicity principle — skip them. **Adopt: ccusage (cost) + a tail of your own `state/journal.md` and `git log` (progress). Optionally wire OTel→Grafana for historical burn charts.** Your verdict-not-numbers stall report is bespoke (subsystem 10).

### 3. Parallel agents in git worktrees + merge/integration
**Verdict: Steal the isolation pattern; adopt a runner only if you want a GUI; keep the "single writer to main" integration loop bespoke.**

This is the most crowded category in the 2026 ecosystem; worktree-per-agent became "load-bearing" for AI coding in Q1 2026. Options with maturity/fit signals:
- **Conductor** (conductor.build): polished, **macOS-only**, free, runs multiple Claude Code/Codex agents in parallel worktrees with a visual diff-first review UI. Best-in-class GUI but platform-locked and GUI-first (fights a headless loop).
- **Crystal** (open source, Electron desktop): multiple Claude Code sessions in parallel worktrees, cross-worktree diff review.
- **vibe-kanban** (`npx vibe-kanban`, Apache-2.0, Rust+TS, cross-platform): kanban board, agent-agnostic, per-task worktree+branch. **Caveat: Bloop, the company behind it, announced a shutdown in early 2026;** it continues as community-maintained open source but hosted services were wound down.
- **claude-squad** (open source, Go, TUI): terminal-first, tmux + worktree per agent. Leanest, most headless-friendly, best fit for your values.
- **Sculptor**: uses containers not just worktrees (stronger isolation).
- Curated lists: `andyrewlee/awesome-agent-orchestrators` (tracks `amux`, `agentbox`, `swarm-protocol`, `wit` — which locks individual functions via Tree-sitter, `subtask`, `wreckit`), and `spillwavesolutions/parallel-worktrees` (a Claude Code *skill* with `sync-worktrees.sh --status|--merge|--interactive` scripts).

**Claude Code native:** `--worktree` flag, subagent `isolation: worktree`, Agent Teams, `/batch`. These give branch-per-agent isolation for free.

**Where they fight your design:** none implement your **"integration loop is the *only* writer to main"** merge-queue discipline. They give N parallel branches and leave the merge to you (usually manual diff review). For the merge side, look at **stacked-branch tooling — Graphite / `git-spice`** — but for a single dev those are likely overkill. **Recommendation: use `git worktree` directly (a native git command, ~2 lines to script) plus claude-squad if you want a TUI overview. Keep your integration loop bespoke — it's a genuine gap.** Steal the `spillwavesolutions/parallel-worktrees` sync scripts as a starting point.

### 4. Edit-scope enforcement / sandboxing
**Verdict: Adopt Claude Code native hooks + sandbox; keep held-out data OS-isolated (your instinct is exactly right).**

Claude Code's native machinery covers your `PreToolUse` design precisely:
- **`PreToolUse` hooks in `.claude/settings.json`**: a hook exiting with code 2 blocks a tool call regardless of permission mode. Matcher on `Edit`/`Write`/`Bash`, reject paths outside the loop's owned set. Exactly your design.
- **`/sandbox`** (v2.1.x): macOS **Seatbelt**, Linux/WSL2 **bubblewrap + socat**. Default write access only to the working dir + `$TMPDIR`; configurable `allowWrite`. `denyRead`/`denyWrite` lists protect settings and secrets, and (v2.1.210+) resolve symlinks so a linked settings file can't be edited through the link.
- **Critical caveat that validates your physical-boundary instinct:** the docs are explicit that `Read`/`Edit` deny rules only block Claude's *built-in file tools*, **not bash subprocesses** — `Read(./.env)` does not stop `cat .env`. Therefore keeping the metric harness and held-out `truth.jsonl` **physically outside the worktree** is not paranoia; it is the *only* reliable defense, because a rule-based deny is bypassable via shell. Combine: put held-out data outside the repo root *and* add it to sandbox `denyRead` as defence-in-depth.

Hook collections to steal from: the ClaudeFast Code Kit ships a tuned `settings.json`; NVIDIA's AI Workbench guide shows a `block-secrets-in-bash.sh` PreToolUse hook and a `denyWrite` list protecting `.claude/hooks` and settings. **For heavier isolation** (untrusted parallel loops), Dagger **Container Use** and Sculptor put each agent in a container. For a single dev, native hooks + sandbox + physical data separation is sufficient and boring. **Adopt native; no need to build.**

### 5. The machine-readable spec ledger
**Verdict: BUILD (bespoke) — but steal the storage model from `beads`.**

This is the heart of your design and there is no drop-in. Two adjacent categories:

- **Requirements traceability** (OpenFastTrace, Doorstop, StrictDoc, Sphinx-Needs, rmtoo, ReqIF tooling): these do requirement→test linking with real rigor. StrictDoc offers bidirectional links and requirements-to-source traceability; Doorstop stores one YAML file per requirement in git. **But:** they are human/auditor-facing (aerospace/medical-device heritage), heavyweight, and — decisively — **none enforce a monotonic status machine gated on a named passing test.** They record links; they don't refuse to advance status until `verify` passes. Adopting one gives you traceability reporting but fights your core invariant.
- **Agent-facing task ledgers:** **`beads`/`bd`** (steveyegge/gastownhall) is the standout — a git-backed graph issue tracker *designed for coding agents*. Per its docs, it stores issues as JSONL in `.beads/` backed by a version-controlled Dolt SQL database ("Taskwarrior meets git"), with hash-based IDs (`bd-a1b2`) to prevent multi-agent merge collisions, `bd ready` (dependency-aware "what's unblocked"), JSON output, and semantic "memory decay" compaction of closed issues; it's written ~92% in Go. It maps well onto your id/priority/status/dependency fields and is built for the Ralph-style "agent picks next ready item" loop. **Backlog.md** and `todo.md` conventions are lighter but flatter.

**The gap only you fill:** your rule that *`status` advances todo→implemented→verified only when the `verify` field's named test exists and passes* is a mechanical invariant no tool enforces. That's ~50 lines of Rust/Python reading `ledger.toml`, cross-checking against `cargo test` output and metric thresholds, and failing the gate on illegal transitions. **Recommendation: keep `ledger.toml` bespoke for the status-gate logic, but seriously consider storing the ledger in `beads` instead of hand-rolled TOML** — you'd get `bd ready`, dependency graphs, and agent-friendly JSON for free, and layer your test-gate check on top as a CI step. If you prefer a single-file TOML for grep-ability and simplicity, that's a defensible choice too.

### 6. Spec-driven development frameworks generally
**Verdict: Skip adopting one wholesale; steal EARS notation and Spec Kit's "constitution" idea.**

The mainstream options as of mid-2026:
- **GitHub Spec Kit**: the most-adopted — **111k GitHub stars as of June 11, 2026** (up 56% from 71k in February), a Python CLI (v0.11.0, June 2026) with 30+ agent integrations and 55+ releases since late February 2026. "Constitution-driven" (a fixed set of project principles). Battle-tested but oriented to greenfield *generation* (spec→plan→tasks→implement), not to *conformance-gating an existing 6000-line prose spec*.
- **Amazon Kiro**: a VS Code fork; launched in public preview mid-2025, reached **GA on May 7, 2026**. spec→design→tasks in EARS notation. Pro tier **$19/month**, free tier 50 requests/month, Bedrock/Claude-backed. IDE-native; wrong shape for a headless loop.
- **OpenSpec** (Fission-AI): lightweight, brownfield-first, `npx`, change-management workflow (propose→apply→archive) with delta specs. Actively developed (recent changelog adds Kiro/Pi support, profiles). The closest philosophically to a disciplined ledger; supports git-worktree-per-change and a `spec-driven-with-adr` schema. Worth reading.
- **BMAD-METHOD**: heavyweight multi-agent (PM/Architect/Scrum-Master/Dev roles), tens of thousands of stars. Explicitly the *opposite* of your "boring runner" value.
- Others: agent-os, Tessl (spec-as-source, well-funded), GSD/"get-shit-done" (meta-prompting), Superpowers (skills framework).

**Honest assessment for your situation:** you already have (a) 6000 lines of prose spec and (b) a *mechanical metric oracle* — a far stronger correctness signal than any of these frameworks provide (they mostly rely on spec text plus generic tests). SDD frameworks solve the "agent has no structure and hallucinates APIs" problem; you've already solved that with your oracle and ledger. Adopting Spec Kit or BMAD would add a generation workflow you don't need and a status model weaker than yours. **Steal specifically:** EARS notation (Easy Approach to Requirements Syntax, developed by Alistair Mavin's team at Rolls-Royce ~2009 — five requirement-syntax patterns that make claims testable, useful when extracting ledger items from prose) and Spec Kit's "constitution" concept (a short fixed set of inviolable rules in your PROMPT.md). Skip the rest. Your bespoke ledger is *better* for your case than any of them.

### 7. The gate / ratchet system
**Verdict: Adopt Bencher for numeric ratchets; keep fmt/clippy/test gates as trivial bash; steal the "exceptions file" pattern from the ratchet literature.**

Your fixed gates (`cargo fmt --check`, `cargo clippy -D warnings`, `cargo test --workspace`) are one-line CI commands — no tooling needed. Use **`cargo-nextest`** as the runner (faster, better machine-readable output for your test-count ratchet). The interesting part is the *ratchets*:

- **Bencher** (bencher.dev, `bencherdev/bencher`) is the single highest-leverage adoption for this subsystem and subsystem 9. Per the docs, it ingests **arbitrary custom measures** via Bencher Metric Format JSON — *"If the value specified is a name or slug and the Measure does not already exist, it will be created for you"* — so `binary_size`, `test_count`, and per-stratum `accuracy` are all first-class. It ships built-in **`--file-size`** (tracks a binary in bytes) and **`--build-time`** measures, proving the non-performance use case. It offers **seven threshold-test models** — `static`, `percentage`, `z_score`, `t_test`, `log_normal`, `iqr`, `delta_iqr` — where **Static** is exactly your hard binary-size ratchet and accuracy floor; the docs state verbatim: *"Static Tests work best when the value of the Metric should stay within a constant range across all Benchmarks, such as code coverage."* Thresholds are keyed on Branch+Testbed+Measure, and **`--error-on-alert`** fails the CI job when a metric crosses a boundary, blocking merge. It's **dual Apache-2.0/MIT licensed** (only "plus" enterprise dirs are proprietary), **self-hostable** (bare metal/Docker/K8s), written in Rust, and actively maintained (latest release v0.6.8, June 2026; ~870 GitHub stars, 6,000+ commits).
- **Binary-size specific:** `cargo-bloat` and the **`orf/cargo-bloat-action`** GitHub Action track per-crate binary size on every PR — but note the original `orf` action is **unmaintained** (a fork, `Reloaded-Project/devops-cargo-bloat-action`, does minimal upkeep). For a *hard ratchet with a baseline file*, the FastLED project's pattern (a single-integer `baseline.txt` asserted by a CI script, ratcheted down per stage) is the exact "hard ratchet + exceptions file" design you described — steal it. `bloaty` (Google) and `twiggy` (for WASM) are the underlying size analyzers.
- **LOC per crate:** `tokei` is the right tool (you named it); wire its JSON output into Bencher as a soft ratchet measure.
- **Betterer** (the JS "ratchet" tool) popularized the pattern (a `.betterer` results file, fail-on-regression, pre-commit hook) but is JS/TS-oriented — steal the *concept* (a checked-in results file that can only improve), not the tool. Notion's per-file `.ratchet.tsv` (counts that auto-decrement as issues are fixed) is another good pattern to mirror.

**Recommendation: put every numeric ratchet — binary size, test count, LOC, and accuracy — into Bencher with `--error-on-alert`.** It replaces the bespoke ratchet-file bookkeeping for all four, gives free historical charts (doubling as subsystem 2 monitoring), and its Static threshold is a literal hard ratchet. Keep only the *ledger-consistency* check bespoke.

### 8. The adversarial verifier
**Verdict: Steal the pattern; run it as a read-only Claude/Codex session with a spec-conformance prompt; optionally add cross-model.**

Existing AI code review maps partially:
- **CodeRabbit** (most-installed, multi-platform GitHub/GitLab/Bitbucket/Azure), **Greptile** (full-codebase indexing, highest raw catch rate but noisiest), **Cursor Bugbot** ($40/user/mo, low-noise, focused on real bugs, IDE-native), **Graphite Diamond**, **Sentry Seer** (only reviewer with a material "critical/high" concentration). In Greptile's July 2025 benchmark of 50 real-world PRs (Python/TypeScript/Go/Java/Ruby), *"Greptile led with an 82% catch rate, 41% higher than Bugbot (58%)… CodeRabbit at 44%, and Graphite at 6%"* — though DeepSource notes this is "not independently validated and uses a small, curated dataset," and Greptile produced ~11 false positives vs CodeRabbit's 2. A separate 3-week/146-PR/679-finding head-to-head found each tool has a distinct "personality": CodeRabbit 96% Major/Minor (style/structure/**conformance**), Seer skewed to critical.
- **Claude Code's own `/review`** and the GitHub app: "a genuine review alternative to CodeRabbit," writes structured comments with confidence scores, and can run in a live shell via `claude-code-action`. **Codex review**, **Danger.js** (rule-based), and **reviewdog** (wraps linters) round out the space.

**Where they fight your design:** all do *generic* PR review ("is this code buggy/insecure?"). None do **spec-conformance review** ("here is spec §4.2 and the implementation — where does it diverge, and file each divergence as a ledger item"). But that's not a product gap to pay for — it's a **prompt + a read-only session + a small script that turns findings into ledger rows.** Your design (separate session, no memory of writing the code, cannot edit, findings become ledger items) is exactly right and is ~1 hook away.

**On your open question — different *model* vs. different *session*:** the practical evidence (the "personalities" study, the LLM-as-judge literature) says a *fresh session of the same model already captures most of the benefit*, because the failure being caught is context/attention-based (the writer "talked itself into" an interpretation), not capability-based. A *different* model adds value mainly through different blind spots and is cheap to add — point a second CLI (`codex`, `gemini`, or a different Claude tier) at the same spec-conformance prompt. **Recommendation: run the verifier as a fresh read-only Claude session first; add a second model as a cheap "panel of judges" only if the same-model verifier rubber-stamps.** Cross-model tooling exists (Promptfoo's "panel of judges," Braintrust) but is overkill; a second CLI invocation is enough.

### 9. Metric/eval harness with held-out sets and CIs
**Verdict: Mostly BUILD (your mechanical oracle is bespoke and correct), but adopt insta for golden replay and Bencher for regression tracking + per-stratum CIs.**

Your oracle is *not* an LLM eval — it's a deterministic replay of go-to-definition against frozen `truth.jsonl`. This is crucial: the LLM-eval platforms (Braintrust, Promptfoo, DeepEval, Ragas, LangSmith, Arize Phoenix) are built around *model-graded* / LLM-as-judge scoring and would be the wrong abstraction. What you actually need:

- **Golden/snapshot replay:** **`insta`** (mitsuhiko, the dominant Rust snapshot crate) with `cargo-insta` for review, plus **`insta-cmd`** for CLI snapshots and **`trycmd`** for command-level golden tests. `expect-test` is a lighter alternative. Run under **`cargo-nextest`**. This gives you the "replay handlers against `truth.jsonl` in under a minute" mechanism with reviewable diffs. Your `truth.jsonl` is essentially a large golden fixture — insta's `assert_json_snapshot!` and redaction features fit.
- **Regression tracking + per-stratum confidence intervals:** **Bencher** again. It accepts an optional `lower_value`/`upper_value` on every reported metric, so you can emit **one benchmark per stratum** (e.g. `gtd::python`, `gtd::rust`) each carrying its own accuracy and CI bounds, tracked independently over time, and gate each with a Static or statistical threshold. One nuance the docs imply: Bencher's *statistical* threshold tests derive variance from the historical distribution of the point value, not from the CI you attach — so if you want the threshold itself to consume your computed CI, use a Static boundary; the attached CIs are stored and plotted per stratum. This is the "so noise isn't mistaken for improvement" guard you wanted, and Bencher is the only tool that can ingest a non-performance accuracy metric at all (CodSpeed is exclusively a performance tool — CPU/memory/walltime — and cannot take arbitrary numbers). Alternatives for hosting custom metrics: Conbench, MLflow, DVC/CML, Weights & Biases — all heavier or ML-experiment-oriented than Bencher.
- **The verdict-not-numbers boundary and the physical held-out-set isolation are bespoke** (and, per subsystem 4, must be OS-level). No tool "shows the loop a verdict, not the numbers" — that's your anti-overfitting invariant and stays custom. The per-stratum CI *statistics* (Wilson intervals on a proportion, etc.) are ~20 lines of Rust or a call to a stats crate; don't over-engineer.

### 10. Journal / decision records / stall detection
**Verdict: Steal ADR tooling conventions; keep git-trailers-as-journal and DECISION-grep bespoke; steal stall constants from existing runners.**

- **ADR / decision records:** the ecosystem is mature — **`adr-tools`** (bash, Nygard format), **Log4brains** (CLI + static-site knowledge base, MADR default, *"only its status can change… your documentation is never out-of-date"* — the immutable-record discipline matches your `decisions/NNN.md`), **MADR** (the template), **pyadr**, **dotnet-adr**, `adr-log`. Your `state/decisions/NNN.md` escalation files *are* ADRs; adopt the **MADR template** and optionally **Log4brains** to render them as a browsable site. But your innovation — **`// DECISION-017: provisional` code tags + `grep -r DECISION-` as the live outstanding-decisions report** — is bespoke and clever; keep it. (Adjacent validation: an arXiv paper, *"Lore: Repurposing Git Commit Messages as a Structured Knowledge Protocol for AI Coding Agents,"* argues implementation-level decisions are exactly what ADRs miss and what commit metadata should capture — support for your git-trailers-as-journal idea.)
- **Git trailers as journal:** git's native `git interpret-trailers` parses/adds structured `key: value` trailers, and `git log --format` can extract them — so your `ledger:`, `tests:`, `loc:`, `binary:`, `decision:` trailers are queryable with stock git, no tool needed. A well-supported, boring, correct choice. Keep it.
- **Stall detection:** no general-purpose "agent loop stall detector" product exists, but **`frankbria/ralph-claude-code` ships the exact heuristics** you want (`MAX_CONSECUTIVE_TEST_LOOPS`, `MAX_CONSECUTIVE_DONE_SIGNALS`, `TEST_PERCENTAGE_THRESHOLD`, session-transition history in `.ralph/.ralph_session_history`). Steal those constants; your "N consecutive iterations with no ledger advance / no test-count increase / no metric movement / no decision resolved" is a superset and stays bespoke — a ~30-line script over your ledger, `git log` trailers, and Bencher history.

2. Set up `PreToolUse` hooks + `/sandbox` with `denyRead`/`denyWrite`; put held-out `truth.jsonl` **physically outside the repo root**.
3. Adopt `ccusage` for cost, `cargo-nextest` for tests, `insta` for `truth.jsonl` golden replay.
4. Stand up **Bencher** (self-hosted or cloud) and pipe binary size (`--file-size`), test count, `tokei` LOC, and per-stratum accuracy into it with `--error-on-alert`. This single step collapses subsystems 2 (charts), 7 (ratchets), and 9 (regression tracking).

**Stage 2 — build the irreducible core (weeks 2-3):** the `ledger.toml` status-gate logic (or `beads` + a gate check), the verdict-not-numbers oracle boundary, the DECISION-grep report, and the integration loop as sole writer to `main`. These are your bespoke value.

**Stage 3 — layer the verifier (week 3+):** a read-only Claude `/review`-style session with a spec-conformance prompt that emits ledger rows; add a second model (Codex/Gemini CLI) only if the same-model verifier rubber-stamps.

**Benchmarks that would change these recommendations:** If you ever run **>3 parallel loops** or onboard a second developer, revisit `claude-squad` (TUI) or Conductor (if macOS) and a real merge queue (Graphite). If your ratchets grow beyond ~5 metrics or you want stakeholder dashboards, Bencher's hosted tier or Grafana becomes worth it. If the same-model verifier's false-negative rate is high, escalate to a genuine cross-model "panel of judges" via Promptfoo.

## Caveats
- **Ecosystem volatility:** this space moves monthly. vibe-kanban's parent (Bloop) shut down in early 2026; the original `cargo-bloat-action` is unmaintained; Claude Code's sandbox/permission semantics changed across v2.1.x point releases. Verify maintenance status at adoption time.
- **Star counts and "maturity" are soft signals.** Several tools cited (wreckit, loopgate_harness, yoshpy-dev/ralph) are young and possibly single-maintainer; treat them as reference designs to read, not dependencies to take.
- **The official `ralph-wiggum` plugin uses same-session re-feeding, which contradicts the fresh-context principle** central to both Ralph and your design — do not adopt it as-is.
- **Rule-based edit denial is not a security boundary.** Claude Code docs are explicit that Read/Edit deny rules don't stop bash subprocesses; only OS-level sandboxing and physical file separation actually protect held-out data. Your instinct here is correct and load-bearing.
- **Bencher's statistical thresholds derive variance from history, not from your supplied CIs** — a subtlety if you expect the boundary test to consume your per-stratum interval directly; use Static boundaries for hard floors/ceilings.
- **A few figures are vendor self-reported or time-sensitive** (Greptile's 82% catch rate on its own small benchmark; exact GitHub star counts for fast-moving repos). These are attributed to their sources and should be treated as of their publication date.
